Verse Logic

Eight Theorems about a Functional Logic Language

The openverse project · November 2026

This is the web edition. Also available as PDF and as Markdown; every program in it was run by openverse fd7aaf3 when this page was built.

Preface

Verse is the programming language Epic Games designed for Unreal Editor for Fortnite and Unreal Engine. It is a functional logic language: besides computing values, an expression may fail, and a failure is caught by the nearest failure context, which rolls back everything the failed attempt did. That one idea gives conditionals, pattern matching, search and transactions a single meaning. It also invites the mathematician’s question: what exactly does a Verse program mean, and which of the language’s promises can be proved?

This book answers that question for openverse, a reference implementation of a deterministic subset of Verse whose semantics is defined in the Lean 4 proof assistant and whose central properties are Lean theorems. Each chapter takes one of those theorems, states it in the notation of logic, proves it in outline, reads the Lean statement line by line, and runs Verse programs that show it at work.

Who this book is for

The book is written for advanced undergraduates and graduate students in mathematics, logic and computer science. You should be at ease with sets, relations and functions; with induction on the natural numbers and on inductively defined relations; with propositional and first-order logic; and with inference rules of the form premise1⋯premisenconclusion𝖭𝖺𝗆𝖾 {\dfrac{\text{premise}_1 \qquad \cdots \qquad \text{premise}_n}{\text{conclusion}}\;\textsf{Name}} A first course on programming languages or type theory helps but is not required. No knowledge of Verse, Lean or games is assumed: Chapter 1 introduces the little of each that we need.

What is proved, and what is trusted

openverse compiles a Verse program in two steps. A front end (lexer, parser and elaborator) translates surface Verse into Verse Core, a small expression language with names resolved to slot and function numbers. The meaning of Verse Core is an inductively defined big-step relation, and every theorem in this book is a theorem about it.

The front end itself is not verified. Instead, each program it produces is checked by functions written in Lean (Prog.check, Prog.checkTypes, Prog.checkControl), and each check is proved to establish the hypotheses of the theorems. This is translation validation: a bug in the front end can make it reject a good program, but it cannot make an accepted program break a promise. Chapter 8 assembles the pieces.

What remains trusted is small and explicit: Lean’s kernel; the statement of the semantics, which is the definition of what Verse Core means; and the reading that this definition captures the language described by the Book of Verse. openverse also contains a C runtime, which is checked against the Lean interpreter by differential testing; some of its components (the rollback store for slots and output, the loader, and the integer arithmetic) are proved separately with the QuickProof tool, and the rest is tested. We touch on that boundary only in Chapter 8.

The programs in this book are tested

Every Verse program in this book was run by openverse when the book was built, and the output printed beneath it is the output openverse produced. Programs shown as rejected were rejected by the front end with the message quoted. Every Lean theorem statement was compared, symbol for symbol, with the statement Lean prints for it in the openverse repository, and every excerpt of Lean source with the source itself. If the book and openverse disagree, the book does not build. To run the programs yourself, paste them into the openverse playground, which runs openverse’s own compiler and runtime in a web browser.

1 Meaning as a Relation

1.1 An opening problem

Here is a small Verse program. Read it before you read its output.

Main():void =
    var Coins:int = 10
    if (set Coins = Coins - 25, Coins >= 0):
        Print("bought the map")
    else:
        Print("cannot afford it: {Coins} coins")

Run in the playground

cannot afford it: 10 coins

The condition of the if assigns to Coins, setting it to −15-15, and then fails, because −15≥0-15 \geq 0 is false and a comparison that does not hold fails in Verse. The else branch then sees Coins as 1010: the assignment has been undone. Verse calls this rollback, and the if condition is a failure context.

What licenses that answer? A programmer would say “run it and see”. A logician would ask for the definition of what the program means, and then derive the answer from it. openverse provides both, and the first theorem of this book says that they agree. The definition is an inductively defined relation, a big-step operational semantics. The procedure is an interpreter, a total Lean function that may run out of “fuel”. The adequacy theorem eval_iff states that the relation holds exactly when the interpreter, given enough fuel, returns the same outcome. Every later chapter proves things about the relation, and gets for free that they hold of the interpreter, and so of openverse run.

1.2 Verse Core

openverse does not give meaning to surface Verse directly. Its front end elaborates the program into Verse Core: a small language whose names are resolved, so that a local variable is a slot number in the frame of the current call and a function is an index into the program. The grammar of Verse Core expressions is

e::=𝗅𝗂𝗍v∣𝗅𝗈𝖼𝖺𝗅i∣𝖺𝗌𝗌𝗂𝗀𝗇ie∣𝗌𝖾𝗊e1e2∣𝗉𝗋𝗂𝗆pe→∣𝖼𝖺𝗅𝗅fe→∣𝗂𝗍𝖾cte∣𝖿𝗈𝗋ie𝑖𝑡e𝑓𝑖𝑙𝑡e𝑏𝑜𝑑𝑦∣𝗅𝗈𝗈𝗉e∣𝖻𝗋𝗄∣𝗋𝖾𝗍e∣𝗉𝗋𝗂𝗇𝗍e∣𝗁𝖾𝖺𝗉oe→ \begin{array}{rcl} e & ::= & \mathsf{lit}\ v \mid \mathsf{local}\ i \mid \mathsf{assign}\ i\ e \mid \mathsf{seq}\ e_1\ e_2 \mid \mathsf{prim}\ p\ \vec{e} \mid \mathsf{call}\ f\ \vec{e} \\ & \mid & \mathsf{ite}\ c\ t\ e \mid \mathsf{for}\ i\ e_{\mathit{it}}\ e_{\mathit{filt}}\ e_{\mathit{body}} \mid \mathsf{loop}\ e \mid \mathsf{brk} \mid \mathsf{ret}\ e \mid \mathsf{print}\ e \mid \mathsf{heap}\ o\ \vec{e} \end{array}

where vv ranges over values, ii over slot numbers, ff over function numbers, pp over primitive operations (++, comparisons, indexing, …) and oo over heap operations (allocation, field reads and writes, class tests). Surface constructs such as not, or, option{…} and and are not primitive: they are derived forms, defined as Verse Core expressions in Chapter 3.

The opening program becomes, after elaboration (abbreviating string literals and the initialization of Coins),

𝗌𝖾𝗊(𝖺𝗌𝗌𝗂𝗀𝗇0(𝗅𝗂𝗍10))(𝗂𝗍𝖾ce𝑡h𝑒𝑛e𝑒𝑙𝑠𝑒)wherec=𝗌𝖾𝗊(𝖺𝗌𝗌𝗂𝗀𝗇0(𝗉𝗋𝗂𝗆−[𝗅𝗈𝖼𝖺𝗅0,𝗅𝗂𝗍25]))(𝗉𝗋𝗂𝗆≥[𝗅𝗈𝖼𝖺𝗅0,𝗅𝗂𝗍0]) \begin{array}{l} \mathsf{seq}\ (\mathsf{assign}\ 0\ (\mathsf{lit}\ 10))\ \big(\mathsf{ite}\ c\ e_{\mathit{then}}\ e_{\mathit{else}}\big) \quad\text{where} \\[2pt] \qquad c \;=\; \mathsf{seq}\ (\mathsf{assign}\ 0\ (\mathsf{prim}\ {-}\ [\mathsf{local}\ 0, \mathsf{lit}\ 25]))\ (\mathsf{prim}\ {\geq}\ [\mathsf{local}\ 0, \mathsf{lit}\ 0]) \end{array}

The command openverse core FILE prints this term for any program.

An evaluation has one of five outcomes:

r::=𝗈𝗄v∣𝖿𝖺𝗂𝗅∣𝖻𝗋𝗄∣𝗋𝖾𝗍v∣𝖾𝗋𝗋k r \ ::=\ \mathsf{ok}\,v \mid \mathsf{fail} \mid \mathsf{brk} \mid \mathsf{ret}\,v \mid \mathsf{err}\,k

Success with a value; Verse failure; a break on its way to the nearest loop; a return on its way to the function boundary; and a runtime error of kind kk (overflow, a type error, a slot or call error, a control error, or an explicit Err()). In Lean:

inductive Res where
  /-- Success with a value. -/
  | ok   : Value → Res
  /-- Verse failure: caught by the nearest failure context, which rolls
      back. -/
  | fail : Res
  /-- `break` travelling to the nearest `loop`. -/
  | brk  : Res
  /-- `return v` travelling to the function boundary. -/
  | ret  : Value → Res
  /-- A runtime error: ends the program. -/
  | err  : ErrKind → Res

A state ss has two parts: the frame s.𝑓𝑟s.\mathit{fr}, the list of values in the slots of the current call, and the global part s.gs.g, which holds the output printed so far and the heap of objects. Both parts are restored on rollback; that the output is too is openverse’s transactional reading of Print.

1.3 The judgment

The meaning of Verse Core is the relation

P⊢⟨s,e⟩⇓⟨r,s′⟩ P \vdash \langle s,\, e \rangle \Downarrow \langle r,\, s' \rangle

read: in program PP, from state ss, expression ee has outcome rr and leaves state s′s'. It is written Eval P s e r s' in Lean, and it is the least relation closed under a set of inference rules, one per Lean constructor. Here are the rules for literals, sequencing and if; the others follow the same pattern.

P⊢⟨s,𝗅𝗂𝗍v⟩⇓⟨𝗈𝗄v,s⟩𝖫𝗂𝗍P⊢⟨s,a⟩⇓⟨𝗈𝗄v,s1⟩P⊢⟨s1,b⟩⇓⟨r,s2⟩P⊢⟨s,𝗌𝖾𝗊ab⟩⇓⟨r,s2⟩𝖲𝖾𝗊-𝖮𝗄 {\dfrac{}{P \vdash \langle s,\, \mathsf{lit}\ v \rangle \Downarrow \langle \mathsf{ok}\,v,\, s \rangle}\;\textsf{Lit}} \qquad {\dfrac{P \vdash \langle s,\, a \rangle \Downarrow \langle \mathsf{ok}\,v,\, s_1 \rangle \qquad P \vdash \langle s_1,\, b \rangle \Downarrow \langle r,\, s_2 \rangle}{P \vdash \langle s,\, \mathsf{seq}\ a\ b \rangle \Downarrow \langle r,\, s_2 \rangle}\;\textsf{Seq-Ok}}

P⊢⟨s,a⟩⇓⟨r,s1⟩r≠𝗈𝗄_P⊢⟨s,𝗌𝖾𝗊ab⟩⇓⟨r,s1⟩𝖲𝖾𝗊-𝖲𝗍𝗈𝗉 {\dfrac{P \vdash \langle s,\, a \rangle \Downarrow \langle r,\, s_1 \rangle \qquad r \neq \mathsf{ok}\,\_}{P \vdash \langle s,\, \mathsf{seq}\ a\ b \rangle \Downarrow \langle r,\, s_1 \rangle}\;\textsf{Seq-Stop}}

P⊢⟨s,c⟩⇓⟨𝗈𝗄v,s1⟩P⊢⟨s1,t⟩⇓⟨r,s2⟩P⊢⟨s,𝗂𝗍𝖾cte⟩⇓⟨r,s2⟩𝖨𝗍𝖾-𝖮𝗄 {\dfrac{P \vdash \langle s,\, c \rangle \Downarrow \langle \mathsf{ok}\,v,\, s_1 \rangle \qquad P \vdash \langle s_1,\, t \rangle \Downarrow \langle r,\, s_2 \rangle}{P \vdash \langle s,\, \mathsf{ite}\ c\ t\ e \rangle \Downarrow \langle r,\, s_2 \rangle}\;\textsf{Ite-Ok}}

P⊢⟨s,c⟩⇓⟨𝖿𝖺𝗂𝗅,s1⟩P⊢⟨s,e⟩⇓⟨r,s2⟩P⊢⟨s,𝗂𝗍𝖾cte⟩⇓⟨r,s2⟩𝖨𝗍𝖾-𝖥𝖺𝗂𝗅 {\dfrac{P \vdash \langle s,\, c \rangle \Downarrow \langle \mathsf{fail},\, s_1 \rangle \qquad P \vdash \langle s,\, e \rangle \Downarrow \langle r,\, s_2 \rangle}{P \vdash \langle s,\, \mathsf{ite}\ c\ t\ e \rangle \Downarrow \langle r,\, s_2 \rangle}\;\textsf{Ite-Fail}}

P⊢⟨s,c⟩⇓⟨r,s1⟩r≠𝗈𝗄_r≠𝖿𝖺𝗂𝗅P⊢⟨s,𝗂𝗍𝖾cte⟩⇓⟨r,s1⟩𝖨𝗍𝖾-𝖲𝗍𝗈𝗉 {\dfrac{P \vdash \langle s,\, c \rangle \Downarrow \langle r,\, s_1 \rangle \qquad r \neq \mathsf{ok}\,\_ \qquad r \neq \mathsf{fail}}{P \vdash \langle s,\, \mathsf{ite}\ c\ t\ e \rangle \Downarrow \langle r,\, s_1 \rangle}\;\textsf{Ite-Stop}}

Three features deserve attention.

Abrupt outcomes propagate. A “stop” rule such as Seq-Stop passes on any outcome other than success: failure, break, return or an error stops the sequence and becomes its outcome. There is one such rule for every construct with subexpressions, and they are what make failure travel outward until something catches it.

Failure contexts catch failure, and roll back. In Ite-Fail the condition fails in state s1s_1, but the else branch starts from ss, the state before the condition ran. The intermediate state s1s_1 is simply dropped. That is the whole of rollback, at the level of the definition: no undo log, no snapshot, just a premise that mentions ss and not s1s_1. (The interpreter and the C runtime implement the same thing with copy-on-write and an undo journal; that they agree with the definition is the point of this chapter and of openverse’s tests.) Note that Ite-Stop does not catch a runtime error or a return: only 𝖿𝖺𝗂𝗅\mathsf{fail} is caught.

The relation is the definition. There is nothing behind it. A Verse Core program means what the rules derive, and the Lean source is the authoritative statement of the rules:

  | ite_ok {s s₁ s₂ c t e v r} :
      Eval P s c (.ok v) s₁ → Eval P s₁ t r s₂ →
      Eval P s (.ite c t e) r s₂
  /-- Rollback: the `else` branch starts from `s`, not from where `c`
      failed. -/
  | ite_fail {s s₁ s₂ c t e r} :
      Eval P s c .fail s₁ → Eval P s e r s₂ →
      Eval P s (.ite c t e) r s₂

Each constructor is an inference rule: the arrows separate premises, the last line is the conclusion, and the variables in braces are universally quantified. The relation is defined mutually with EvalList, for argument lists evaluated left to right, and EvalFor, for the iterations of a for.

A whole program runs to outcome rr with output oo when calling Main from the initial state (an empty frame, no output, an empty heap) derives rr and leaves output oo:

RunsPro:⇔∃𝑓𝑟h.P⊢⟨s0,𝖼𝖺𝗅𝗅𝑚𝑎𝑖𝑛[]⟩⇓⟨r,⟨𝑓𝑟,⟨o,h⟩⟩⟩ \mathrm{Runs}\ P\ r\ o \quad :\Longleftrightarrow\quad \exists\, \mathit{fr}\ \mathit{h}.\ \ P \vdash \langle s_0,\, \mathsf{call}\ \mathit{main}\ [] \rangle \Downarrow \langle r,\, \langle \mathit{fr}, \langle o, h\rangle\rangle \rangle

1.4 The interpreter

A relation is a definition, not a program. To run Verse Core, openverse has a reference interpreter, eval, a Lean function of type

eval:Prog→ℕ→St→Expr→Option(Res×St). \mathrm{eval} : \mathrm{Prog} \to \mathbb{N} \to \mathrm{St} \to \mathrm{Expr} \to \mathrm{Option}(\mathrm{Res} \times \mathrm{St}).

The natural number is fuel. Every recursive call spends one unit, so eval is defined by structural recursion on the fuel and Lean accepts it as a total function, even though Verse programs need not terminate. When the fuel runs out, eval returns none; otherwise it returns the outcome and the final state. Its if case mirrors the three rules:

  | n+1, s, .ite c t e => match eval P n s c with
      | none => none
      | some (.ok _, s₁) => eval P n s₁ t
      | some (.fail, _) => eval P n s e

On failure the interpreter, like Ite-Fail, discards the state the condition left and continues from s. This is the function that openverse run executes, and the C runtime is a transcription of it.

1.5 The theorem

Adequacy (eval_iff) and fuel irrelevance (eval_fuel_irrelevant)

For every program PP, states s,s′s, s', expression ee and outcome rr: P⊢⟨s,e⟩⇓⟨r,s′⟩⇔∃n∈ℕ.evalPnse=𝗌𝗈𝗆𝖾(r,s′). P \vdash \langle s,\, e \rangle \Downarrow \langle r,\, s' \rangle \iff \exists n \in \mathbb{N}.\ \ \mathrm{eval}\ P\ n\ s\ e = \mathsf{some}\,(r, s'). Moreover, for all fuels n1,n2n_1, n_2 and results x1,x2x_1, x_2: evalPn1se=𝗌𝗈𝗆𝖾x1∧evalPn2se=𝗌𝗈𝗆𝖾x2⇒x1=x2. \mathrm{eval}\ P\ n_1\ s\ e = \mathsf{some}\ x_1 \ \wedge\ \mathrm{eval}\ P\ n_2\ s\ e = \mathsf{some}\ x_2 \ \Longrightarrow\ x_1 = x_2 .

In Lean, as printed by #check:

@eval_iff : ∀ {P : Prog} {s : St} {e : Expr} {r : Res} {s' : St},
  Eval P s e r s' ↔ ∃ n, eval P n s e = some (r, s')
@eval_fuel_irrelevant : ∀ {P : Prog} {n₁ n₂ : Nat} {s : St} {e : Expr}
    {x₁ x₂ : Res × St},
  eval P n₁ s e = some x₁ → eval P n₂ s e = some x₂ → x₁ = x₂

Read the first line left to right. The @ and the braces mark implicit arguments, which Lean infers at each use; logically they are universal quantifiers, ∀Psers′\forall P\, s\, e\, r\, s'. Eval P s e r s' is our judgment. ↔︎ is ⇔\iff, and ∃ n, eval P n s e = some (r, s') is the right-hand side, with some the constructor of Option. The second statement uses right-nested implications, A → B → C, which is Lean’s curried spelling of A∧B⇒CA \wedge B \Rightarrow C. The axioms Lean reports for both proofs are propext and Quot.sound, the standard ones; there is no sorry.

Fuel irrelevance says that fuel decides whether the interpreter finishes, never what it returns. Adequacy says that what it returns is exactly what the rules derive.

1.6 The proof

The two directions are proved separately, as eval_sound and eval_complete, each mutually with its counterparts for argument lists and for loops.

Soundness (⇐\Leftarrow): if evalPnse=𝗌𝗈𝗆𝖾(r,s′)\mathrm{eval}\ P\ n\ s\ e = \mathsf{some}\,(r, s') then P⊢⟨s,e⟩⇓⟨r,s′⟩P \vdash \langle s,\, e \rangle \Downarrow \langle r,\, s' \rangle. By induction on nn. With n=0n = 0 the interpreter returns none, so there is nothing to prove. With n+1n + 1, case on ee: each clause of eval makes recursive calls with fuel nn, whose results the induction hypothesis turns into derivations, and these are exactly the premises of the rule that matches the clause. For example, if the condition of an ite returns 𝗌𝗈𝗆𝖾(𝖿𝖺𝗂𝗅,s1)\mathsf{some}(\mathsf{fail}, s_1) and the else branch 𝗌𝗈𝗆𝖾(r,s2)\mathsf{some}(r, s_2), the hypothesis gives P⊢⟨s,c⟩⇓⟨𝖿𝖺𝗂𝗅,s1⟩P \vdash \langle s,\, c \rangle \Downarrow \langle \mathsf{fail},\, s_1 \rangle and P⊢⟨s,e⟩⇓⟨r,s2⟩P \vdash \langle s,\, e \rangle \Downarrow \langle r,\, s_2 \rangle, and Ite-Fail concludes. Small lemmas about the interpreter’s “bind” combinators (bindR_some, bindR_stop) do the bookkeeping of the stop rules.

Completeness (⇒\Rightarrow) is the subtler direction, and the proof strengthens the statement before proving it. The naive induction fails in the Seq-Ok case: the hypotheses give fuel n1n_1 that suffices for aa and fuel n2n_2 that suffices for bb, but the interpreter runs both aa and bb with the same fuel. One needs to know that more fuel does not hurt. Rather than proving monotonicity separately, openverse builds it into the induction:

Eventually

Eventuallyfy:⇔∃N.∀m≥N.fm=𝗌𝗈𝗆𝖾y \mathrm{Eventually}\ f\ y \quad :\Longleftrightarrow\quad \exists N.\ \forall m \geq N.\ f\ m = \mathsf{some}\ y 

def Eventually (f : Nat → Option α) (y : α) : Prop :=
  ∃ n, ∀ m, n ≤ m → f m = some y

The completeness lemma proves, by induction on the derivation, that

P⊢⟨s,e⟩⇓⟨r,s′⟩⇒Eventually(λn.evalPnse)(r,s′). P \vdash \langle s,\, e \rangle \Downarrow \langle r,\, s' \rangle \ \Longrightarrow\ \mathrm{Eventually}\ (\lambda n.\ \mathrm{eval}\ P\ n\ s\ e)\ (r, s').

Now the Seq-Ok case is easy. The hypotheses give thresholds N1N_1 for aa and N2N_2 for bb; take N=max(N1,N2)+1N = \max(N_1, N_2) + 1. For any m≥Nm \geq N write m=k+1m = k + 1; then k≥N1k \geq N_1 and k≥N2k \geq N_2, so the interpreter’s two recursive calls with fuel kk return the right results, and the seq clause combines them. Every case has this shape: the threshold of a rule is one more than the maximum of its premises’ thresholds. The call_ok case, where the derivation of the callee’s body is a premise, is no different, which is why recursive functions need no special treatment: a derivation is a finite tree, even when the program it describes calls itself.

Adequacy follows by taking m=Nm = N, and fuel irrelevance is now a corollary rather than a lemma. Suppose the interpreter returns x1x_1 with fuel n1n_1 and x2x_2 with fuel n2n_2. By soundness both are derivable; by completeness, each is eventually the interpreter’s answer, from thresholds N1N_1 and N2N_2. At fuel max(N1,N2)\max(N_1, N_2) the interpreter returns both, so 𝗌𝗈𝗆𝖾x1=𝗌𝗈𝗆𝖾x2\mathsf{some}\ x_1 = \mathsf{some}\ x_2 and x1=x2x_1 = x_2. The same three lines will prove determinism in Chapter 2.

1.8 Limits and readings

  • Big-step semantics cannot see divergence. A non-terminating program has no derivation. By adequacy, a configuration has no derivation exactly when the interpreter returns none at every fuel, that is, when the interpreter runs forever: there are no stuck configurations. Ill-shaped ones (a slot out of range, a call with the wrong number of arguments, an operation on values of the wrong type) derive an error outcome rather than no outcome, and Chapters 5 and 8 show that checked programs never produce those errors.
  • The interpreter is total only because of fuel. eval is a function in Lean’s logic, so it must terminate on every input; fuel is the price. The theorem shows that the price is paid only in time, never in meaning.
  • The definition is trusted. Adequacy relates two Lean objects. That the rules capture the language described by the Book of Verse is not a theorem; it is the reading openverse documents and tests.

2 One Program, One Answer

2.1 An opening problem

Logic programming usually means search. A Prolog query may have many answers, produced in an order that depends on the search strategy, and the Verse Calculus, the core calculus behind Verse, has an operator of choice, e1∣e2e_1 \mid e_2, under which one expression has several values. Yet a Verse program run by openverse prints the same thing every time:

Main():void =
    Pairs := for (X := 1..3, Y := 1..3, X < Y) { X * 10 + Y }
    for (P : Pairs) { Print("{P}") }

Run in the playground

12

23

The for explores a search space (all pairs with X<YX < Y), but in a fixed order: generators left to right, each in ascending order, filters pruning as they go. Is this an accident of the implementation, or a property of the language that openverse implements? For the programmer, the question is whether a test that passed once will pass again, and whether the Lean interpreter and the C runtime can disagree on a correct program. For the logician, it is whether the relation of Chapter 1 is the graph of a partial function. The theorem of this chapter says that it is.

2.2 The theorem

Determinism (Eval.det, Runs.det)

For every program PP, state ss and expression ee: P⊢⟨s,e⟩⇓⟨r1,s1⟩∧P⊢⟨s,e⟩⇓⟨r2,s2⟩⇒r1=r2∧s1=s2. P \vdash \langle s,\, e \rangle \Downarrow \langle r_1,\, s_1 \rangle \ \wedge\ P \vdash \langle s,\, e \rangle \Downarrow \langle r_2,\, s_2 \rangle \ \Longrightarrow\ r_1 = r_2 \ \wedge\ s_1 = s_2 . Consequently a program has at most one run: RunsPr1o1∧RunsPr2o2⇒r1=r2∧o1=o2. \mathrm{Runs}\ P\ r_1\ o_1 \ \wedge\ \mathrm{Runs}\ P\ r_2\ o_2 \ \Longrightarrow\ r_1 = r_2 \ \wedge\ o_1 = o_2 .

Equivalently, with the uniqueness quantifier ∃≤1\exists^{\leq 1} (“at most one”): ∀Pse.∃≤1(r,s′).P⊢⟨s,e⟩⇓⟨r,s′⟩. \forall P\, s\, e.\ \ \exists^{\leq 1} (r, s').\ \ P \vdash \langle s,\, e \rangle \Downarrow \langle r,\, s' \rangle . Note “at most”: a program that runs forever has no outcome, and the theorem says nothing about it.

@Eval.det : ∀ {P : Prog} {s : St} {e : Expr} {r₁ : Res} {s₁ : St} {r₂ : Res}
    {s₂ : St},
  Eval P s e r₁ s₁ → Eval P s e r₂ s₂ → r₁ = r₂ ∧ s₁ = s₂
@Runs.det : ∀ {P : Prog} {r₁ : Res} {o₁ : List Nat} {r₂ : Res}
    {o₂ : List Nat},
  Runs P r₁ o₁ → Runs P r₂ o₂ → r₁ = r₂ ∧ o₁ = o₂

The output oo is a List Nat: the bytes printed (in a typed program, each a number below 256; the type Nat does not enforce it). The states s1,s2s_1, s_2 in Eval.det include the frame and the heap, so determinism covers more than printed output: the values of all variables, every object, and even the addresses at which objects were allocated.

2.3 Why it could fail

A relation defined by inference rules is deterministic only if the rules are designed for it. Two things could go wrong.

Overlapping rules. If two rules can conclude about the same expression, with compatible premises, there may be two derivations with different outcomes. Look again at the three ite rules of Chapter 1. Their first premises are about the same condition cc, from the same state ss, with outcomes 𝗈𝗄v\mathsf{ok}\,v, 𝖿𝖺𝗂𝗅\mathsf{fail}, and “anything else”:

P⊢⟨s,c⟩⇓⟨r,s1⟩r≠𝗈𝗄_r≠𝖿𝖺𝗂𝗅P⊢⟨s,𝗂𝗍𝖾cte⟩⇓⟨r,s1⟩𝖨𝗍𝖾-𝖲𝗍𝗈𝗉 {\dfrac{P \vdash \langle s,\, c \rangle \Downarrow \langle r,\, s_1 \rangle \qquad r \neq \mathsf{ok}\,\_ \qquad r \neq \mathsf{fail}}{P \vdash \langle s,\, \mathsf{ite}\ c\ t\ e \rangle \Downarrow \langle r,\, s_1 \rangle}\;\textsf{Ite-Stop}}

The side conditions r≠𝗈𝗄_r \neq \mathsf{ok}\,\_ and r≠𝖿𝖺𝗂𝗅r \neq \mathsf{fail} are what keep Ite-Stop from overlapping the other two. Every construct of Verse Core follows the same discipline: its rules are told apart by the outcome of the subexpression evaluated first (a success, a failure where that matters, or anything else), and, where a successful value can still be ill-shaped, by a side condition on that value (Assign-Bad for a slot outside the frame, Call-Bad for a missing function, …). (In Lean the side condition “not a success” is written r.isOk = false.)

Nondeterministic primitives. A rule whose conclusion is not a function of its premises would break determinism even without overlaps: a rule for choice, say, with conclusions 𝗈𝗄v1\mathsf{ok}\,v_1 and 𝗈𝗄v2\mathsf{ok}\,v_2 for e1∣e2e_1 \mid e_2, or an allocation rule that picks some fresh address. openverse has neither. Choice is in the subset (from the Verse Calculus; the Book of Verse does not describe it yet), but ordered: e₁ | e₂ gives e₁’s values, then e₂’s, and it adds no rule to Verse Core, because the front end compiles it into iteration over the alternatives. Concurrency (spawn, race, sync, Sleep) adds no rule either: the front end compiles it into ordinary Core code. The next section shows both. And allocation takes the next address, the current size of the heap:

  | .new t, vs, ⟨out, heap⟩ =>
      (.ok (.ref heap.size), ⟨out, heap.push ⟨t, vs⟩⟩)

Primitive operations are functions too (Prim.apply, HeapOp.apply), so each rule’s conclusion is determined by its premises.

2.4 The proof

There are two proofs, and it is instructive to see both.

The textbook proof is by induction on the first derivation, inverting the second. Suppose 𝒟1\mathcal{D}_1 derives P⊢⟨s,e⟩⇓⟨r1,s1⟩P \vdash \langle s,\, e \rangle \Downarrow \langle r_1,\, s_1 \rangle and 𝒟2\mathcal{D}_2 derives P⊢⟨s,e⟩⇓⟨r2,s2⟩P \vdash \langle s,\, e \rangle \Downarrow \langle r_2,\, s_2 \rangle; we show r1=r2r_1 = r_2 and s1=s2s_1 = s_2 by induction on 𝒟1\mathcal{D}_1. The last rule of 𝒟2\mathcal{D}_2 must be a rule for the same construct. Take e=𝗂𝗍𝖾cte′e = \mathsf{ite}\ c\ t\ e' and 𝒟1\mathcal{D}_1 ending in Ite-Ok, with premises P⊢⟨s,c⟩⇓⟨𝗈𝗄v,s′1⟩P \vdash \langle s,\, c \rangle \Downarrow \langle \mathsf{ok}\,v,\, s'_1 \rangle and P⊢⟨s′1,t⟩⇓⟨r1,s1⟩P \vdash \langle s'_1,\, t \rangle \Downarrow \langle r_1,\, s_1 \rangle.

  • If 𝒟2\mathcal{D}_2 ends in Ite-Fail, its first premise is P⊢⟨s,c⟩⇓⟨𝖿𝖺𝗂𝗅,s″⟩P \vdash \langle s,\, c \rangle \Downarrow \langle \mathsf{fail},\, s'' \rangle. The induction hypothesis for the first premise of 𝒟1\mathcal{D}_1 gives 𝗈𝗄v=𝖿𝖺𝗂𝗅\mathsf{ok}\,v = \mathsf{fail}: impossible.
  • If 𝒟2\mathcal{D}_2 ends in Ite-Stop, its first premise gives an outcome r≠𝗈𝗄_r \neq \mathsf{ok}\,\_; again the hypothesis gives 𝗈𝗄v=r\mathsf{ok}\,v = r, a contradiction.
  • If 𝒟2\mathcal{D}_2 ends in Ite-Ok, with premises P⊢⟨s,c⟩⇓⟨𝗈𝗄v′,s″⟩P \vdash \langle s,\, c \rangle \Downarrow \langle \mathsf{ok}\,v',\, s'' \rangle and P⊢⟨s″,t⟩⇓⟨r2,s2⟩P \vdash \langle s'',\, t \rangle \Downarrow \langle r_2,\, s_2 \rangle, the hypothesis gives v=v′v = v' and s′1=s″s'_1 = s''; so the second premises start in the same state, and the hypothesis for them gives r1=r2r_1 = r_2 and s1=s2s_1 = s_2.

Every case of every construct is like one of these: an “ok” rule against a “stop” rule is a contradiction through the side condition, and two rules of the same kind agree by the hypotheses applied left to right, each premise starting where the previous one ended. For call, the hypothesis for the argument list gives the same arguments, hence the same callee and frame, and the hypothesis for the body gives the same result.

openverse’s proof is three lines long, because Chapter 1 already did the work:

theorem Eval.det {P : Prog} {s e r₁ s₁ r₂ s₂}
    (h₁ : Eval P s e r₁ s₁) (h₂ : Eval P s e r₂ s₂) :
    r₁ = r₂ ∧ s₁ = s₂ := by
  obtain ⟨n₁, H₁⟩ := eval_iff.mp h₁
  obtain ⟨n₂, H₂⟩ := eval_iff.mp h₂
  have := eval_fuel_irrelevant H₁ H₂
  simp only [Prod.mk.injEq] at this
  exact this

In words: by adequacy, the interpreter returns (r1,s1)(r_1, s_1) at some fuel n1n_1 and (r2,s2)(r_2, s_2) at some fuel n2n_2; by fuel irrelevance these results are equal; equality of pairs is equality of components. The obtain lines destructure the existentials that eval_iff.mp (the left-to-right direction of the biconditional) produces.

The logic behind the short proof is worth stating as a principle.

Determinism for free

If a relation R⊆A×BR \subseteq A \times B satisfies Rab⇔∃n.fna=𝗌𝗈𝗆𝖾bR\,a\,b \iff \exists n.\ f\ n\ a = \mathsf{some}\ b for a family of partial functions fnf\ n that agree wherever they are defined, then RR is the graph of a partial function, hence deterministic. Defining an interpreter and proving it adequate yields determinism without a separate induction.

The textbook induction is not needed at all, but its work is done elsewhere. Fuel irrelevance came from the Eventually form of completeness, an induction on a single derivation; it never compares two rules. The exclusivity that the textbook proof checks case by case is built into eval: a Lean function defined by pattern matching has one clause for each shape of input, so it cannot return two answers. Adequacy transfers that property from the function to the relation.

Runs.det follows from Eval.det: two runs are two derivations from the same initial state for the same expression, 𝖼𝖺𝗅𝗅𝑚𝑎𝑖𝑛[]\mathsf{call}\ \mathit{main}\ [], so their final states are equal, hence so are their outputs (congrArg (fun s : St => s.g.out)).

2.6 Limits and readings

  • Determinism by fixing orders. The theorem is about openverse’s subset, and the subset fixes every order that could vary. Choice gives its values in spatial order, the reading the Verse Calculus paper takes to keep choice deterministic. The places a choice may appear are listed in docs/LANGUAGE.md. Concurrency fixes the order in which tasks go on and counts time in ticks. Both are compiled into Core code, so they add no rule for Eval.det to cover.
  • At most one, not exactly one. Eval.det gives uniqueness, not existence. A diverging program has no outcome; Chapter 1 explained why that is the only way to have none.
  • The C runtime is deterministic by testing. Lean proves determinism of the definition and the reference interpreter. The C interpreter is a transcription checked by differential testing, under sanitizers. Its rollback store and loader have separate machine-checked proofs (Chapter 8).
  • Readings. Several of the orders above are openverse’s choices where the Book of Verse is silent: output inside a failed failure context is rolled back, a failing for body makes the whole for fail (as in the Verse Calculus), and maps compare in order. Determinism holds given these readings, which the rules fix.

3 Failure Is Not False

3.1 An opening problem

In most languages a condition is a Boolean expression: it evaluates to true or false, and evaluating it may have side effects that persist whichever way it goes. In Verse a condition is an expression that either succeeds or fails, and when it fails, its side effects disappear:

Main():void =
    var X:int = 1
    if (set X = 2, X = 2, set X = 3, X = 4):
        Print("never")
    Print("X = {X}")
    if (set X = 2, X = 2, set X = 3):
        Print("committed: X = {X}")

Run in the playground

X = 1
committed: X = 3

The first condition makes two assignments and passes one test before the last test fails, and then it is as if none of it had happened. The second succeeds, and its assignments stay. A condition is a transaction: it commits on success and aborts on failure.

For a programmer this is the feature that makes Verse conditions safe to write as searches (“find a key, take it, open the chest”) without cleanup code for the paths that do not work out. For a logician it raises a question about connectives. If failure plays the role of falsity, what are not, or and and, and how do they interact with effects? This chapter proves the rollback law for if, then derives the others from it.

3.2 The theorem

Rollback (ite_rollback)

If the condition cc fails from state ss, then for every outcome rr and state s′s' P⊢⟨s,c⟩⇓⟨𝖿𝖺𝗂𝗅,s1⟩⇒(P⊢⟨s,𝗂𝗍𝖾cte⟩⇓⟨r,s′⟩⇔P⊢⟨s,e⟩⇓⟨r,s′⟩). P \vdash \langle s,\, c \rangle \Downarrow \langle \mathsf{fail},\, s_1 \rangle \ \Longrightarrow\ \Big(P \vdash \langle s,\, \mathsf{ite}\ c\ t\ e \rangle \Downarrow \langle r,\, s' \rangle \iff P \vdash \langle s,\, e \rangle \Downarrow \langle r,\, s' \rangle\Big).

Once the condition has failed, the whole if is indistinguishable from its else branch run from the original state: the same outcomes, the same final states. Nothing that cc did, and nothing in s1s_1, can be observed.

@ite_rollback : ∀ {P : Prog} {s s₁ : St} {c t e : Expr} {r : Res} {s' : St},
  Eval P s c Res.fail s₁ → (Eval P s (c.ite t e) r s' ↔ Eval P s e r s')

c.ite t e is Lean’s dot notation for Expr.ite c t e. The hypothesis names the failed run of the condition, and the conclusion is a biconditional for all rr and s′s': an equivalence of the two expressions, from ss.

3.3 The derived forms

Law 2 is the surprising one, and it deserves a logician’s reading. In classical logic ¬¬A↔A\neg\neg A \leftrightarrow A. Here not not e succeeds exactly when e succeeds, but it is not e: it returns void instead of ee’s value, and it leaves the state exactly as it found it, discarding every effect of ee (and, at the surface, every name ee binds). It is a pure test of whether ee would succeed. The analogy with intuitionistic logic is apt: there, ¬¬A\neg\neg A asserts that AA cannot be refuted without supplying a witness for AA; here, not not e asserts that ee succeeds without supplying its value or keeping its effects.

3.4 The proof

Rollback. The direction ⇐\Leftarrow is the rule Ite-Fail itself, applied to the hypothesis P⊢⟨s,c⟩⇓⟨𝖿𝖺𝗂𝗅,s1⟩P \vdash \langle s,\, c \rangle \Downarrow \langle \mathsf{fail},\, s_1 \rangle and the given derivation for ee. For ⇒\Rightarrow, invert the derivation of the ite: its last rule is one of the three.

  • Ite-Ok would need P⊢⟨s,c⟩⇓⟨𝗈𝗄v,s″⟩P \vdash \langle s,\, c \rangle \Downarrow \langle \mathsf{ok}\,v,\, s'' \rangle for some v,s″v, s''. With the hypothesis, Eval.det gives 𝗈𝗄v=𝖿𝖺𝗂𝗅\mathsf{ok}\,v = \mathsf{fail}, which is false.
  • Ite-Stop would need P⊢⟨s,c⟩⇓⟨r″,s″⟩P \vdash \langle s,\, c \rangle \Downarrow \langle r'',\, s'' \rangle with r″≠𝖿𝖺𝗂𝗅r'' \neq \mathsf{fail}; determinism gives r″=𝖿𝖺𝗂𝗅r'' = \mathsf{fail}, a contradiction.
  • Ite-Fail has the premise P⊢⟨s,e⟩⇓⟨r,s′⟩P \vdash \langle s,\, e \rangle \Downarrow \langle r,\, s' \rangle, which is what we want.
theorem ite_rollback {P s s₁ c t e r s'} (hc : Eval P s c .fail s₁) :
    Eval P s (.ite c t e) r s' ↔ Eval P s e r s' := by
  constructor
  · intro h
    cases h with
    | ite_ok h1 _ => exact absurd (Eval.det h1 hc).1 (by simp)
    | ite_fail _ h2 => exact h2
    | ite_stop h1 _ hf => exact absurd (Eval.det h1 hc).1 hf
  · intro h; exact .ite_fail hc h

Notice the dependency: rollback, a statement about one branch, needs determinism, a statement about all derivations. Without Chapter 2, the if could have a second derivation in which the same condition succeeds, and the equivalence would fail. The tactic cases h with is exactly the inversion above, one line per rule; absurd closes a case from a contradiction.

not. Unfold 𝗇𝗈𝗍e\mathsf{not}\ e to 𝗂𝗍𝖾e(𝗉𝗋𝗂𝗆𝑓𝑎𝑖𝑙[])(𝗅𝗂𝗍𝑣𝑜𝑖𝑑)\mathsf{ite}\ e\ (\mathsf{prim}\ \mathit{fail}\ [])\ (\mathsf{lit}\ \mathit{void}) and invert a successful derivation. If it is Ite-Stop, the outcome is not 𝗈𝗄_\mathsf{ok}\,\_, contradicting the hypothesis. So it is Ite-Fail: ee failed from ss, and the else branch, the literal void, succeeded from ss without changing it (rule Lit). Hence v=𝑣𝑜𝑖𝑑v = \mathit{void} and s′=ss' = s.

not not. Apply the law for not to the outer negation: s′=ss' = s, and the inner 𝗇𝗈𝗍e\mathsf{not}\ e failed from ss. Invert that failure: it cannot come from Ite-Fail, whose else branch succeeds; nor from Ite-Stop, whose outcome is not 𝖿𝖺𝗂𝗅\mathsf{fail}; so it is Ite-Ok, whose first premise is a success of ee from ss.

These are the laws a programmer relies on without thinking: an or fallback never sees a half-finished left side; option{…} of a failure has no effect; not never leaks.

3.6 Limits and readings

  • Effects inside the condition of a successful if are kept, and so are the bindings, which the then branch can see. Rollback is about failure only.
  • Output is rolled back because openverse makes Print transactional: the output is part of the state. The Book of Verse does not say what happens to output in a failed context; this is openverse’s reading. The heap is rolled back too: object writes and allocations (Chapter 7).
  • return inside a failure context leaves the function without rolling back what the condition did (another openverse reading): a 𝗋𝖾𝗍v\mathsf{ret}\,v outcome is propagated by Ite-Stop, not caught.
  • The laws are about Verse Core. The front end elaborates surface not, or and option{} into exactly these definitions, which openverse core lets you check on any program; the scoping rule that names defined in the operands of and, or and not do not escape is enforced by the front end.

4 Who May Fail

4.1 An opening problem

If any expression may fail, any function call may fail, and a programmer would have to treat every call as a possible failure. Verse avoids this with an effect: a function that may fail is marked <decides>, is called with square brackets, and may be called only where failure is caught. Everything else is guaranteed not to fail. Here is the discipline at work:

Key(N:int)<decides>:int = N > 0

Safe(N:int):int =
    if (K := Key[N]) then K else 0

Main():void =
    Print("{Safe(5)} {Safe(-5)}")

Run in the playground

5 0

Key fails for non-positive NN; Safe calls it inside an if condition, so Safe itself cannot fail, needs no <decides>, and is called with parentheses. The front end enforces the discipline. The same call outside a failure context is rejected:

First(A:[]int):int = A[0]

Main():void =
    Print("{First(array{4})}")

Run in the playground

Rejected: this expression can fail, but it is not in a failure context

Indexing can fail (the index may be out of range), and First is not <decides>. The programmer’s question: is the check sound, so that a function that passed it really never fails? The logician’s: the check is a syntactic predicate, and the property is semantic; what invariant connects them, and why does it survive recursion? This chapter answers both.

4.2 The analysis

The front end decides, for each expression, whether it may fail: whether it contains a failable primitive, or a call to a <decides> function, outside every failure context it contains. In Verse Core this is a recursive function mayFailP:Expr→𝔹\mathrm{mayFail}_P : \mathrm{Expr} \to \mathbb{B}:

The two lines that matter are the last two. The condition cc of an ite does not appear on the right: it is a failure context, so its failure is caught. Likewise the filter of a for, whose failure skips an element. In Lean:

  | .call f es =>
    (match P.fns[f]? with
      | some fn => fn.decides
      | none => false) || Expr.mayFailList P es
  -- the condition is a failure context: its failure is caught
  | .ite _ t e => t.mayFail P || e.mayFail P
  -- the filter is a failure context: its failure skips the element
  | .forE _ it _ body => it.mayFail P || body.mayFail P

The analysis of a call trusts the callee’s declaration (fn.decides), not its body. That is what makes it modular and cheap, and it is also why soundness needs a global hypothesis: the declarations must be honest.

Effect soundness of a program

EffectSound(P):⇔∀𝑓𝑛∈P.𝑓𝑛𝑠.¬𝑓𝑛.𝑑𝑒𝑐𝑖𝑑𝑒𝑠⇒¬mayFailP(𝑓𝑛.𝑏𝑜𝑑𝑦) \mathrm{EffectSound}(P) \quad :\Longleftrightarrow\quad \forall \mathit{fn} \in P.\mathit{fns}.\ \ \neg\,\mathit{fn}.\mathit{decides} \ \Rightarrow\ \neg\,\mathrm{mayFail}_P(\mathit{fn}.\mathit{body}) Every function not declared <decides> has a body that may not fail.

def Prog.EffectSound (P : Prog) : Prop :=
  ∀ fn ∈ P.fns, fn.decides = false → fn.body.mayFail P = false

  P.EffectSound → ∀ {s : St} {e : Expr} {r : Res} {s' : St},
    Eval P s e r s' → Expr.mayFail P e = false → r ≠ Res.fail
@Runs.no_fail : ∀ {P : Prog},
  P.EffectSound →

The structure of the statement is typical of effect systems: a syntactic judgment (¬mayFail\neg\mathrm{mayFail}) implies a semantic property (no failure outcome), under an invariant of the whole program (EffectSound). Note what is not claimed: the expression may still raise a runtime error, break, return, or diverge. Only failure is excluded. P.fns[P.main]? = some fn says that fn is Main’s definition (? is safe indexing into the list of functions, returning an Option).

4.4 The proof

By induction on the derivation of P⊢⟨s,e⟩⇓⟨r,s′⟩P \vdash \langle s,\, e \rangle \Downarrow \langle r,\, s' \rangle, mutually with the corresponding statements for EvalList and EvalFor. Assume EffectSound(P)\mathrm{EffectSound}(P) throughout. Most cases are immediate: a stop rule propagates the outcome of a subexpression that, by the definition of mayFail\mathrm{mayFail}, may not fail either, so the induction hypothesis applies. Four cases carry the idea.

Primitives. A successful argument list leads to p.applyv→p.\mathrm{apply}\ \vec{v}, and a lemma, Prim.apply_ne_fail, says that a primitive that is not failable never returns 𝖿𝖺𝗂𝗅\mathsf{fail}. The failable ones are the comparisons, indexing and indexed update, the division family, ?, and false?.

ite. If the derivation ends in Ite-Ok or Ite-Fail, the outcome is the outcome of tt or of ee, and both may not fail by hypothesis, so the induction hypothesis on that branch concludes. The condition’s failure, the one thing that mayFail\mathrm{mayFail} ignored, is exactly what Ite-Fail consumes. If it ends in Ite-Stop, the outcome is the condition’s, and the side condition of the rule says it is not 𝖿𝖺𝗂𝗅\mathsf{fail}. Notice that this case uses no induction hypothesis about the condition at all: soundness here is a property of the rules, which do not let a failed condition escape.

for. The filter’s failure is consumed by EvalFor.skip; the body’s failure would be propagated, but the body may not fail.

Calls. This is the case that seems to need more than induction. The derivation ends in

Since ¬mayFail(𝖼𝖺𝗅𝗅fe→)\neg\mathrm{mayFail}(\mathsf{call}\ f\ \vec{e}), the callee is not <decides>. By EffectSound(P)\mathrm{EffectSound}(P) its body may not fail. The derivation of the body is a premise of this rule, hence a subderivation, and the induction hypothesis applies to it: r≠𝖿𝖺𝗂𝗅r \neq \mathsf{fail}. Finally retOf\mathrm{retOf}, which turns 𝗋𝖾𝗍v\mathsf{ret}\,v into 𝗈𝗄v\mathsf{ok}\,v, maps non-failures to non-failures (retOf_ne_fail).

The call case is where the global invariant earns its keep. A recursive function’s body contains calls to the function itself, so an induction on the syntax of expressions would go round in circles. Induction on the derivation does not: each call’s body has its own, strictly smaller, derivation. The price is the one we met in Chapter 1: the theorem speaks only of evaluations that finish.

Runs.no_fail is the instance e=𝖼𝖺𝗅𝗅𝑚𝑎𝑖𝑛[]e = \mathsf{call}\ \mathit{main}\ [], with no arguments to fail and mayFail\mathrm{mayFail} reduced to 𝑚𝑎𝑖𝑛\mathit{main}’s decides flag.

Where does EffectSound(P)\mathrm{EffectSound}(P) come from for a real program? The front end does not prove it; Lean checks it. The Boolean function Prog.checkEffectSound tests every function, and a two-line lemma shows that it returning true implies the proposition:

def Prog.checkEffectSound (P : Prog) : Bool :=
  P.fns.all fun fn => fn.decides || !(fn.body.mayFail P)

Every program the front end emits passes this check (Chapter 8), so the theorem applies to every accepted program.

A <decides> function propagates failure to its caller; a context catches it. Here Pick fails out of range, and the for clause skips those indices:

The analysis is conservative. It is syntactic, so it rejects some programs that could never fail. Index 0 of a three-element array literal always exists, but indexing is failable, and the program is rejected anyway:

This is the usual trade of a static analysis: soundness and predictability in exchange for completeness. A theorem cannot rescue completeness here; deciding exactly which expressions can fail is as hard as deciding termination.

4.6 Limits and readings

  • Only failure is excluded. A function without <decides> may still overflow, call Err(), or run forever. Runtime errors are discussed in Chapter 8.
  • Soundness is relative to the declarations. Eval.no_fail assumes EffectSound, which is checked, not assumed, for programs from the front end. A Verse Core program built by hand could lie about a function, and then the theorem would not apply to it.
  • Failable primitives are fixed by the semantics (Prim.failable): the comparisons, indexing and indexed update, the division family (Floor, Ceil, Quotient, Mod, which fail when the divisor is zero), ?, and the always-failing false?; among heap operations, only casts. Array methods such as Find and Slice are elaborated into code built from these. That division by zero fails, rather than raising an error, follows the Book of Verse.

5 Well-Typed Programs Do Not Go Wrong

5.1 An opening problem

A value of a subclass can stand wherever its superclass is expected, and so can an array of them:

shape := class<abstract>:
    Area():int

square := class(shape):
    Side:int
    Area<override>():int = Side * Side

rect := class(shape):
    W:int
    H:int
    Area<override>():int = W * H

Total(Shapes:[]shape):int =
    var Sum:int = 0
    for (S : Shapes) { set Sum += S.Area() }
    Sum

Main():void =
    Squares:[]square = array{square{Side := 2}, square{Side := 3}}
    Print("{Total(Squares)}")
    Mixed:[]shape = array{square{Side := 1}, rect{W := 2, H := 5}}
    Print("{Total(Mixed)}")
    for (S : Mixed, Sq := square[S]) { Print("a square of side {Sq.Side}") }

Run in the playground

a square of side 1

Total expects a []shape and receives a []square, with no conversion at run time. The last line casts each shape to square; the cast fails for the rectangle, and the for clause skips it. Is this safe? In Java, array covariance is famously unsound: storing a rect into a square[] seen as a shape[] fails only at run time, with an ArrayStoreException. Here, does any typed program ever apply an operation to a value of the wrong shape?

Milner’s slogan, “well-typed programs do not go wrong”, is a theorem about a particular language. This chapter states and proves it for Verse Core, with classes, subtyping, a heap and generic functions, and explains why Verse’s covariant arrays are sound where Java’s are not.

5.2 Types, values, heaps

Verse Core types are

τ::=𝑖𝑛𝑡∣𝑙𝑜𝑔𝑖𝑐∣𝑐h𝑎𝑟∣𝑓𝑙𝑜𝑎𝑡∣[]τ∣𝑡𝑢𝑝𝑙𝑒(τ1,…,τn)∣?τ∣αj∣𝑟𝑒𝑓Cτ→ \tau \ ::=\ \mathit{int} \mid \mathit{logic} \mid \mathit{char} \mid \mathit{float} \mid [\,]\tau \mid \mathit{tuple}(\tau_1, \ldots, \tau_n) \mid {?}\tau \mid \alpha_j \mid \mathit{ref}\ C\ \vec{\tau}

where void is the empty tuple, string is []𝑐h𝑎𝑟[\,]\mathit{char}, αj\alpha_j is the jj-th type parameter of a generic function (Chapter 6), and 𝑟𝑒𝑓Cτ→\mathit{ref}\ C\ \vec{\tau} is a reference to an object whose class is one of the set CC of class tags, with type arguments τ→\vec{\tau}. A surface class type such as shape elaborates to the set of the concrete classes at or below it, so shape is 𝑟𝑒𝑓{𝑠𝑞𝑢𝑎𝑟𝑒,𝑟𝑒𝑐𝑡}[]\mathit{ref}\ \{\mathit{square}, \mathit{rect}\}\ [] (a tag is a class’s index in definition order).

Subtyping τ≤τ′\tau \leq \tau' is a decidable relation (VTy.sub): references are ordered by inclusion of class sets (and prefixes of type arguments), arrays, options and tuples are covariant, and otherwise a type is below only itself.

C⊆C′τ′→ prefix of τ→𝑟𝑒𝑓Cτ→≤𝑟𝑒𝑓C′τ′→τ≤τ′[]τ≤[]τ′τ≤τ′?τ≤?τ′ \frac{C \subseteq C' \quad \vec{\tau'} \text{ prefix of } \vec{\tau}}{\mathit{ref}\ C\ \vec{\tau} \leq \mathit{ref}\ C'\ \vec{\tau'}} \qquad \frac{\tau \leq \tau'}{[\,]\tau \leq [\,]\tau'} \qquad \frac{\tau \leq \tau'}{{?}\tau \leq {?}\tau'}

Values are typed relative to a heap typing Ξ\Xi, a list assigning each heap address a class tag and type arguments. We write Ξ⊨v:τ\Xi \models v : \tau for hasTy Ξ v τ = true. Integers have type 𝑖𝑛𝑡\mathit{int}, an array has type []τ[\,]\tau when all its elements have type τ\tau, and a reference 𝗋𝖾𝖿a\mathsf{ref}\ a has type 𝑟𝑒𝑓Cτ→\mathit{ref}\ C\ \vec{\tau} when Ξ(a)\Xi(a) is a class in CC whose type arguments extend τ→\vec{\tau}:

def hasTy (Ξ : HeapTy) : Value → VTy → Bool
  | .int _, .int => true
  | .logic _, .logic => true
  | .char c, .char => decide (c < 256)
  | .float _, .float => true
  | .arr vs, .arr t => allTy Ξ vs.toList t
...
  | .ref a, .ref ts args => match Ξ[a]? with
    | some (t, args') => ts.contains t && args.isPrefixOf args'
    | none => false
  | .ref a, .vref es args => match Ξ[a]? with
    | some (t, args') => es.any fun e =>
        e.1 == t && args.isPrefixOf (e.2.map (VTy.inst args'))
    | none => false
  | _, _ => false

The vref case is a view. An interface that some class gives type arguments other than its own first ones, as both(t, u) := class(container(t), sink(u)) gives sink its second, has a type with one entry per class below it: the class’s tag and the interface’s type arguments written over that class’s own (from both, sink’s view is [var 1], both’s second argument). A reference has such a type when its object’s class has an entry whose view, instantiated at the object’s type arguments, extends the interface’s arguments.

A heap hh is well typed under Ξ\Xi, written HeapOKSΞh\mathrm{HeapOK}\ S\ \Xi\ h, when Ξ\Xi has one entry per object, and each object’s fields have the types that its class declares in the signature SS, instantiated at its type arguments (which agree with any its class fixes, as Chapter 6 explains). A frame is well typed, FrameOKΞΓ𝑓𝑟\mathrm{FrameOK}\ \Xi\ \Gamma\ \mathit{fr}, when slot ii holds a value of type Γi\Gamma_i.

5.3 The typing judgment

Expressions are typed by S;Γ;ρ⊢e:τS;\Gamma;\rho \vdash e : \tau (Typed S Γ ρ e τ): in a program with signatures SS, in a function whose slots have types Γ\Gamma and whose result type is ρ\rho, expression ee has type τ\tau. A selection of the rules:

S;Γ;ρ⊢c:σS;Γ;ρ⊢t:τS;Γ;ρ⊢e:τS;Γ;ρ⊢𝗂𝗍𝖾cte:τ𝖳-𝖨𝗍𝖾 {\dfrac{S;\Gamma;\rho \vdash c : \sigma \qquad S;\Gamma;\rho \vdash t : \tau \qquad S;\Gamma;\rho \vdash e : \tau}{S;\Gamma;\rho \vdash \mathsf{ite}\ c\ t\ e : \tau}\;\textsf{T-Ite}}

S;Γ;ρ⊢e:ρS;Γ;ρ⊢𝗋𝖾𝗍e:τ𝖳-𝖱𝖾𝗍S;Γ;ρ⊢𝖻𝗋𝗄:τ𝖳-𝖡𝗋𝗄 {\dfrac{S;\Gamma;\rho \vdash e : \rho}{S;\Gamma;\rho \vdash \mathsf{ret}\ e : \tau}\;\textsf{T-Ret}} \qquad {\dfrac{}{S;\Gamma;\rho \vdash \mathsf{brk} : \tau}\;\textsf{T-Brk}}

Two features stand out. In T-Ite the condition may have any type σ\sigma: in Verse a condition is not a Boolean, it is anything that may fail. And return and break have every type, since they never produce a value where they stand; ρ\rho records what return must deliver.

5.4 The theorem

The outcome of a typed expression is described by a predicate ResOKΞτρr\mathrm{ResOK}\ \Xi\ \tau\ \rho\ r:

def ResOK (Ξ : HeapTy) (τ ρ : VTy) : Res → Prop
  | .ok v => hasTy Ξ v τ = true
  | .ret v => hasTy Ξ v ρ = true
  | .err k => k ≠ .type
  | .fail => True
  | .brk => True

A success has the expression’s type; a return carries the function’s result type; an error is not a type error; failure and break are unconstrained. The third line is where “does not go wrong” lives.

Type safety (Eval.typed, Runs.typed)

Let PP be typed with signatures SS (ProgTypedPS\mathrm{ProgTyped}\ P\ S). If P⊢⟨s,e⟩⇓⟨r,s′⟩,S;Γ;ρ⊢e:τ, P \vdash \langle s,\, e \rangle \Downarrow \langle r,\, s' \rangle, \qquad S;\Gamma;\rho \vdash e : \tau, FrameOKΞΓs.𝑓𝑟,HeapOKSΞs.h𝑒𝑎𝑝, \mathrm{FrameOK}\ \Xi\ \Gamma\ s.\mathit{fr}, \qquad \mathrm{HeapOK}\ S\ \Xi\ s.\mathit{heap}, then there is a heap typing Ξ′⊒Ξ\Xi' \sqsupseteq \Xi (an extension: Ξ\Xi is a prefix of Ξ′\Xi') with FrameOKΞ′Γs′.𝑓𝑟,ResOKΞ′τρr,HeapOKSΞ′s′.h𝑒𝑎𝑝. \mathrm{FrameOK}\ \Xi'\ \Gamma\ s'.\mathit{fr}, \qquad \mathrm{ResOK}\ \Xi'\ \tau\ \rho\ r, \qquad \mathrm{HeapOK}\ S\ \Xi'\ s'.\mathit{heap}. For whole programs: if Main has type ()→τ() \to \tau, then every run has r≠𝖾𝗋𝗋𝑡𝑦𝑝𝑒r \neq \mathsf{err}\,\mathit{type}, ends in a well-typed heap, and a successful run returns a value of type τ\tau.

@Eval.typed : ∀ {P : Prog} {S : Sigs},
  ProgTyped P S →
    ∀ {s : St} {e : Expr} {r : Res} {s' : St} {Γ : List VTy} {ρ τ : VTy}
        {Ξ : HeapTy},
      Eval P s e r s' →
        Typed S Γ ρ e τ →
          FrameOK Ξ Γ s.fr →
            HeapOK S Ξ s.g.heap →
              ∃ Ξ', FrameOK Ξ' Γ s'.fr ∧ ResOK Ξ' τ ρ r ∧
                HeapOK S Ξ' s'.g.heap ∧ Ξ <+: Ξ'

Ξ <+: Ξ' is Lean’s notation for “is a prefix of”. The theorem is preservation in big-step form, and here it also does the work of progress. In a small-step semantics, progress says a typed term is a value or can step. In big-step form that is not implied by preservation in general, because a stuck configuration simply has no derivation. It is in this semantics because, as Chapter 1 noted, there are no stuck configurations: every ill-shaped step derives an explicit error, so “goes wrong” means “derives 𝖾𝗋𝗋𝑡𝑦𝑝𝑒\mathsf{err}\,\mathit{type}”, which ResOK\mathrm{ResOK} excludes.

@Runs.typed : ∀ {P : Prog} {S : Sigs},
  ProgTyped P S →
    ∀ {τ : VTy} {r : Res} {out : List Nat},
      S.fns[P.main]? = some ([], τ) →
        Runs P r out →
          r ≠ Res.err ErrKind.type ∧
            ∃ fr heap,
              Eval P Prog.initSt (Expr.call P.main []) r
                  { fr := fr, g := { out := out, heap := heap } } ∧
                ∃ Ξ, HeapOK S Ξ heap ∧
                  ∀ (v : Value), r = Res.ok v → hasTy Ξ v τ = true

Supporting it is the soundness of subsumption:

@hasTy_sub : ∀ {Ξ : HeapTy} (t u : VTy) (v : Value),
  t.sub u = true → hasTy Ξ v t = true → hasTy Ξ v u = true

5.5 The proof

Subsumption is sound (hasTy_sub), by induction on tt. For references: if Ξ(a)∈C\Xi(a) \in C and C⊆C′C \subseteq C' then Ξ(a)∈C′\Xi(a) \in C', and a prefix of a prefix is a prefix. For arrays: if every element has type τ\tau and τ≤τ′\tau \leq \tau', every element has type τ′\tau' by the induction hypothesis. This is the whole reason covariant arrays are sound in Verse: a Verse array is an immutable value. set A[i] = x does not write into a shared array; it builds a new array and assigns it to the variable A, whose declared type ΓA\Gamma_A the assignment rule checks xx against. Java’s unsoundness needs an array object that two variables of different static types share; Verse has no such thing. (Objects are shared, and their fields are typed invariantly: set on a field checks the field’s declared type.)

Preservation. openverse does not prove Eval.typed by induction on the derivation but, as in Chapter 2, through the interpreter: by strong induction on the fuel, for the statement “if eval P n s e = some (r, s') and the hypotheses hold, then the conclusion holds”, and then transports the result to Eval with eval_iff. The reason is the call case. A callee’s body is an initialization prefix followed by the user’s code bb; the frame satisfies Γ\Gamma only after the prefix has run, so the induction hypothesis is needed for bb evaluated from that later state, at whatever smaller fuel remains (eval_initPrefixE). That evaluation is not a subderivation of anything in hand, so structural induction on derivations does not reach it, while strong induction on fuel does. The ingredients:

  1. Inversion up to subsumption. A typing derivation may end with any number of T-Sub steps. The proof peels them off: if e:τe : \tau then e:τ0e : \tau_0 by a non-subsumption rule, for some τ0≤τ\tau_0 \leq \tau; it proves the conclusion at τ0\tau_0, then lifts it with hasTy_sub (ResOK_sub).
  2. Heap typings only grow. Allocation appends an object, and the proof appends its class and type arguments to Ξ\Xi. A field write replaces a field with a value of the field’s type, leaving Ξ\Xi unchanged. Values typed under Ξ\Xi remain typed under any extension (hasTy_mono), which is why the conclusion is stated with Ξ⊑Ξ′\Xi \sqsubseteq \Xi'.
  3. Primitives are type safe (prim_typed): a primitive applied to values of its argument types returns ResOK\mathrm{ResOK} of its result type. This is a finite case analysis over the primitive table.
  4. Calls instantiate the callee’s signature with a substitution θ\theta for its type parameters (Chapter 6), and the callee’s body is typed with its own Γ\Gamma, which the new frame satisfies because the arguments have the parameter types and the other slots are initialized first (the elaborator emits an initialization prefix; initPrefixE).
  5. Rollback is harmless. In Ite-Fail the else branch runs from the original state ss, typed under the original Ξ\Xi; whatever Ξ\Xi the failed condition reached is discarded with its state.

Runs.typed instantiates preservation at the call of Main, from the initial state, whose frame and heap are empty. When the program has classes, there is one more step. Class-typed variables start as prototype objects (one per non-parametric concrete class), so the Verse Core Main is a prelude that allocates the prototypes and then calls the user’s Main. Runs.typed evaluates the prelude (Eval.of_protoPrelude) and applies preservation to that inner call, from the heap of prototypes, which ProgTyped\mathrm{ProgTyped} requires to be well typed (PreludeOK).

The type checker is sound. Where does ProgTypedPS\mathrm{ProgTyped}\ P\ S come from? openverse runs a bidirectional type checker, tc, on every program the front end emits, together with a certificate of each function’s slot types. tc either returns a type or fails, and tc_sound proves that a returned type is derivable:

@tc_sound : ∀ {S : Sigs} {Γ : List VTy} {ρ : VTy} {e : Expr} {m : Option VTy}
    {τ : VTy},
  tc S Γ ρ e m = some τ → Typed S Γ ρ e τ

m is the optional expected type that bidirectional checking pushes down. A corollary, Prog.checkTypes_sound, lifts the result to whole programs. Only soundness is proved: a correct program that tc cannot type is rejected, which is safe.

5.7 Limits and readings

  • Type errors are excluded; other errors are not. Overflow and Err() remain possible, and so do slot, call and control errors unless the program also passes checkWellScoped and checkControl, which Chapter 8 adds.
  • The trusted part is the statement. The typing rules and hasTy\mathrm{hasTy} are definitions. That they match Verse’s surface type system is the elaborator’s business, and it is not proved: what is proved is that whatever the elaborator emits, if it passes checkTypes, does not go wrong.
  • Prototypes. Class-typed slots start as shared prototype objects rather than as an uninitialized value. Verse code always assigns such a variable before reading it, so the prototypes are never observed; they exist to make every slot hold a value of its type from the start.
  • Comparability. = on values of different surface types that coincide in Verse Core (an enum and an int, say) is rejected by the front end, a reading documented in docs/LANGUAGE.md; the Core rule types = at the type of its left operand.
  • Types the front end lowers. rational, any and refinement types (type{_X:int where 0 <= _X, _X <= 120}) have no Verse Core type of their own: a rational is the tuple of its numerator and denominator in lowest terms, an any is void, and a refined int or float is just its base, with the cast age[X] a comparison that may fail. The theorem covers these Core images. That a refined value stays within its bounds, or that a rational stays in lowest terms, is the front end’s business: tested, not proved. (float is different: it is a Core type, with its own case in hasTy\mathrm{hasTy}.)

Find is used at string and at int. There are two classical ways to make such code safe. A template system (C++) type-checks each instantiation separately, after substituting the type: errors appear at use sites, and code is duplicated. A parametric system (ML, Haskell, Java generics) checks the definition once, with t opaque, and guarantees that every instantiation is then fine. Verse is parametric: the body of Find is checked once, and operations not valid for every t are rejected even if Find is never called.

For a programmer, this means a library function that compiles cannot break at a new type. For a logician, it is a statement about a typing judgment under substitution, the substitution lemma, one of the workhorses of type theory. openverse proves it for Verse Core, and its proof of type safety uses it at every call.

6.2 Type variables and substitutions

A generic function’s types may mention type variables α0,α1,…\alpha_0, \alpha_1, \ldots (VTy.var j): its jj-th type parameter. A substitution θ:ℕ→VTy\theta : \mathbb{N} \to \mathrm{VTy} replaces each variable by a type, and acts on types homomorphically:

θ(αj)=θj,θ([]τ)=[]θ(τ),θ(𝑡𝑢𝑝𝑙𝑒(τ→))=𝑡𝑢𝑝𝑙𝑒(θτ→),θ(𝑖𝑛𝑡)=𝑖𝑛𝑡,… \theta(\alpha_j) = \theta\,j, \qquad \theta([\,]\tau) = [\,]\theta(\tau), \qquad \theta(\mathit{tuple}(\vec\tau)) = \mathit{tuple}(\theta\vec\tau), \qquad \theta(\mathit{int}) = \mathit{int}, \ \ldots

We write θΓ\theta\Gamma for the pointwise image of a list of slot types. The typing rule for calls is where substitutions enter: a call may instantiate the callee’s signature (p→,τ)(\vec{p}, \tau) with any θ\theta, provided the arguments have the instantiated parameter types.

S.𝑓𝑛𝑠f=(p→,τ)S;Γ;ρ⊢e→:θp→S;Γ;ρ⊢𝖼𝖺𝗅𝗅fe→:θτ𝖳-𝖢𝖺𝗅𝗅 {\dfrac{S.\mathit{fns}_f = (\vec{p}, \tau) \qquad S;\Gamma;\rho \vdash \vec{e} : \theta\vec{p}}{S;\Gamma;\rho \vdash \mathsf{call}\ f\ \vec{e} : \theta\tau}\;\textsf{T-Call}} 

  /-- A call instantiates the callee's type variables with any `θ`. -/
  | call {f es ps τ} (θ : Nat → VTy) : S.fns[f]? = some (ps, τ) →
      TypedL S Γ ρ es (ps.map (VTy.subst θ)) →
      Typed S Γ ρ (.call f es) (τ.subst θ)

No value has a type variable as its type: Ξ⊨v:αj\Xi \models v : \alpha_j is always false. A value can have a type mentioning a variable only where the variable is not inhabited: the empty array has type []αj[\,]\alpha_j, and the empty option type ?αj{?}\alpha_j.

6.3 The theorem

The substitution lemma (Typed.subst)

If the signatures SS are closed (ClosedS\mathrm{Closed}\ S: the prototype objects’ type arguments are closed), then for every substitution θ\theta: S;Γ;ρ⊢e:τ⇒S;θΓ;θρ⊢e:θτ. S;\Gamma;\rho \vdash e : \tau \ \Longrightarrow\ S;\theta\Gamma;\theta\rho \vdash e : \theta\tau . 

@Typed.subst : ∀ {S : Sigs} {Γ : List VTy} {ρ : VTy},
  S.Closed →
    ∀ (θ : Nat → VTy) {e : Expr} {τ : VTy},
      Typed S Γ ρ e τ →
        Typed S (List.map (VTy.subst θ) Γ) (VTy.subst θ ρ) e (VTy.subst θ τ)

The same expression ee is typed on both sides: nothing is recompiled or re-elaborated. A typing derivation with variables is a proof schema, and every instance of the schema is a proof. That is the logical content of “checked once”.

The hypothesis Closed\mathrm{Closed} looks technical, and it is. Literals in Verse Core may be references to the prototype objects that exist before Main (Chapter 5), and their types must not mention variables, or a literal typed at αj\alpha_j-dependent arguments could not be retyped. The front end always satisfies it. The pins need no hypothesis. A class may fix its parent’s type arguments, as int_box := class(box(int)) fixes box’s to int, or repeat and relate them, as dup(t) := class(pair(t, t)) (below) pins both of pair’s to its own t. SS records the pins, which may mention the class’s own variables.

6.4 The proof

By induction on the typing derivation, mutually with the lemma for lists of expressions (TypedL.subst). Most cases rebuild the same rule from the induction hypotheses, because the rules are uniform in the types: they never inspect whether a type is a variable. Three cases need a lemma, and the classes that fix type arguments need an argument of their own.

Literals. T-Lit has the premise hasTyS.𝑝𝑟𝑜𝑡𝑜𝑠vτ\mathrm{hasTy}\ S.\mathit{protos}\ v\ \tau. We need hasTyS.𝑝𝑟𝑜𝑡𝑜𝑠v(θτ)\mathrm{hasTy}\ S.\mathit{protos}\ v\ (\theta\tau): typing of values is stable under substitution (hasTy_subst). By induction on vv and τ\tau: an integer has type 𝑖𝑛𝑡=θ(𝑖𝑛𝑡)\mathit{int} = \theta(\mathit{int}); the empty array has every array type; a reference’s type arguments are a prefix of a prototype’s, which are closed, so θ\theta does not change them. A variable itself is never the type of a value, so that case is vacuous.

Subsumption. T-Sub has the premise τ≤τ′\tau \leq \tau'; we need θτ≤θτ′\theta\tau \leq \theta\tau'. Subtyping is stable under substitution (VTy.sub_subst), by structural recursion on τ\tau (subtyping is a Boolean function, VTy.sub, not an inductive relation); a variable is below only itself, and θαj≤θαj\theta\alpha_j \leq \theta\alpha_j by reflexivity.

Calls. The derivation ends in T-Call with its own substitution θ′\theta': the arguments have types θ′p→\theta'\vec{p} and the call has type θ′τ\theta'\tau. The induction hypothesis turns the argument typings into typings at θ(θ′p→)\theta(\theta'\vec{p}). Composition of substitutions, θ∘θ′:=λj.θ(θ′j)\theta \circ \theta' := \lambda j.\ \theta(\theta'\,j), satisfies

θ(θ′σ)=(θ∘θ′)σfor every type σ \theta(\theta'\sigma) = (\theta \circ \theta')\,\sigma \qquad\text{for every type }\sigma

(VTy.subst_comp), so the arguments have the types (θ∘θ′)p→(\theta\circ\theta')\vec{p}, and T-Call with the substitution θ∘θ′\theta\circ\theta' gives the call the type (θ∘θ′)τ=θ(θ′τ)(\theta\circ\theta')\tau = \theta(\theta'\tau), as required:

  | _, _, .call θ' hs hes => by
    have h := TypedL.subst hS θ hes
    rw [List.map_map] at h
    have h' := Typed.call (fun j => (θ' j).subst θ) hs
      (by rw [← VTy.substL_comp]; simpa [Function.comp_def] using h)
    rwa [← VTy.subst_comp] at h'

This case is why the rule T-Call quantifies over every θ\theta, rather than fixing one per call site: the set of typings must be closed under composition. The class of substitutions being all functions ℕ→VTy\mathbb{N} \to \mathrm{VTy} makes it so.

Pins. Creating an object requires its type arguments to agree with its class’s pins: each pinned argument is its pin instantiated at the arguments. Substitution commutes with that instantiation, so the agreement survives θ\theta whatever the pins are (VTy.pinsOK_subst). The call of an override in a class with pins goes further, and looks at the types themselves: it is typed under a refinement μ\mu, a most general substitution that makes the receiver’s type arguments agree with the pins (int for box(t)’s t). The front end finds it by first-order unification, itself verified in Lean (Core/Unify.lean). After θ\theta, either some ρ′\rho' makes the instance agree, so that ρ′∘θ\rho' \circ \theta makes the original arguments agree and therefore factors through the most general one, (ρ′∘θ)∘μ=ρ′∘θ(\rho' \circ \theta) \circ \mu = \rho' \circ \theta (PinRefines.factor), which carries the typing over to the instance’s own refinement; or none does, and the call is typed as unreachable (Typed.dispatch_none), as it then is at every instance.

6.5 How type safety uses it

The proof of Eval.typed (Chapter 5) reaches a call of a generic function ff at instance θ\theta. The callee’s body was typed once, generically, with slot types Γf\Gamma_f and result type ρf\rho_f mentioning variables. The substitution lemma retypes it with θΓf\theta\Gamma_f and θρf\theta\rho_f. The new frame holds the actual arguments and void in the other slots; after the body’s initialization prefix has run (eval_initPrefixE), it satisfies θΓf\theta\Gamma_f, and the induction hypothesis applies to the rest of the body at the instance. No step of the proof ever looks inside a type variable.

There is one more obstacle, and it is a design problem rather than a proof problem. Every slot of a Verse Core frame must hold a value of its type from the start (FrameOK), and the elaborator initializes local slots before the body runs. But a slot of type αj\alpha_j has no default value: there is no value of an unknown type. openverse’s solution is to pass one hidden argument per type parameter, a value of that type, chosen by the caller, and initialize such slots from it. For

6.7 Limits and readings

  • The lemma is about typing, not about behavior. It does not say that a generic function behaves uniformly at all types (Reynolds’ parametricity, the “theorems for free”). openverse’s hidden witnesses are never observed, so uniform behavior is plausible, but it is not a theorem here.
  • Inference is unverified. The front end infers each call’s type arguments by first-order matching against the expected result type and then the arguments (docs/LANGUAGE.md). It need not be complete or even correct: the checker re-checks each call against the instantiated signature, and only that check is part of the trusted argument.
  • Restrictions of the subset: no generic Main, and no explicit type arguments for generic functions; several constraints on one type parameter are not supported (nor, at the time of writing, in the Book). Named parameters work in generic functions as elsewhere: Gn(X:t, ?Y:t = X where t:type) is called as Gn(1, ?Y := 2) or Gn("a"). A class may override where it fixes, repeats or relates its parent’s type arguments, or has type arguments of its own (pairE), and such an override may be <suspends>. docs/LANGUAGE.md lists what is still unsupported.

7 Look but Do Not Touch

7.1 An opening problem

Values in Verse are immutable, but objects are not: a class may have var fields, an object is shared by every reference to it, and a write through one reference is seen through all the others. Rollback extends to the heap:

chest := class:
    var Gold:int = 0

Deposit(C:chest, N:int)<transacts>:void =
    set C.Gold += N

Peek(C:chest)<reads>:int = C.Gold

Main():void =
    Mine := chest{}
    Alias := Mine
    Deposit(Mine, 5)
    Print("Alias sees {Peek(Alias)}")
    if (Deposit(Mine, 100), Peek(Mine) > 1000):
        Print("rich")
    Print("after the failed attempt: {Peek(Mine)}")

Run in the playground

Alias sees 5
after the failed attempt: 5

Mutation makes reasoning harder: to know what a call does, one must know which objects it may change. Verse answers with heap effects, specifiers on a function’s signature: <computes> (no access to mutable state), <reads> (may read var fields), <allocates> (may construct objects with mutable state), <writes> (may set var fields), and <transacts> (all of these). Peek above is <reads>. The programmer wants to know that calling Peek cannot change the chest. The logician recognizes a frame property: an analysis on the syntax implies that a whole region of the state is untouched. This chapter proves it.

7.2 The analysis

The front end checks each body against its function’s declared effects, and records in Verse Core, for each function, a single bit: whether it may writes. A function declared <computes>, <reads> or <allocates> (or a combination without <writes>) has 𝑤𝑟𝑖𝑡𝑒𝑠=⊥\mathit{writes} = \bot. In Verse Core the only operation that changes an existing object is the field write 𝗁𝖾𝖺𝗉(𝑠𝑒𝑡k)[r,v]\mathsf{heap}\ (\mathit{set}\ k)\ [r, v], and the analysis is:

Writes the heap

Compare the ite line with Chapter 4’s mayFail\mathrm{mayFail}, which ignored the condition. Here the condition counts. 7.3 What “untouched” means

A function that does not write may still allocate, so its heap may grow. The right relation between the global state before and after is that every object that existed is still there, at the same address, with the same fields:

Keeps

g≼g′:⇔∀ao.g.h𝑒𝑎𝑝[a]=𝗌𝗈𝗆𝖾o⇒g′.h𝑒𝑎𝑝[a]=𝗌𝗈𝗆𝖾o g \preceq g' \ :\Longleftrightarrow\ \forall a\, o.\ \ g.\mathit{heap}[a] = \mathsf{some}\ o \ \Rightarrow\ g'.\mathit{heap}[a] = \mathsf{some}\ o (Glob.keeps g g'). It is reflexive and transitive: a preorder.

def Glob.keeps (g g' : Glob) : Prop :=
  ∀ (a : Nat) (o : Obj), g.heap.toList[a]? = some o →
    g'.heap.toList[a]? = some o

Note what ≼\preceq does not constrain: the output (a non-writing function may print), new objects, and the frame.

      P.fns[f]? = some fn →
        fn.writes = false → Expr.writesHeapList P es = false →
          Eval P s (Expr.call f es) r s' → s.g.keeps s'.g

The second theorem has no WriteSound hypothesis: it takes P.check = true, the Boolean check every accepted program passes (Chapter 8), and derives WriteSound from it (Prog.check_writeSound). The theorem holds whatever the outcome rr: even if the call fails, raises an error or returns early, no existing object has changed.

7.5 The proof

By induction on the derivation, mutually for lists and for iterations, assuming WriteSound(P)\mathrm{WriteSound}(P). The global state threads through evaluation, and each case composes the steps with the transitivity of ≼\preceq.

  • Leaves (Lit, Local, Brk) do not change the state: reflexivity.
  • Sequencing and arguments: s.g≼s1.g≼s2.gs.g \preceq s_1.g \preceq s_2.g by the hypotheses, then transitivity. The same for every rule with several premises evaluated in order.
  • Heap operations. Since ¬writesHeap\neg\,\mathrm{writesHeap}, the operation is not a field write. Allocation pushes an object at the end of the heap, which keeps every existing address; reads, class tests and casts leave the heap as it is.
  • print changes the output, which ≼\preceq ignores.
  • Calls. The arguments keep the heap by the hypothesis. The callee does not write, so by WriteSound\mathrm{WriteSound} its body does not write, and the hypothesis for the body’s derivation, a premise of Call-Ok, gives that the body keeps the heap. The call’s final state takes the caller’s frame and the body’s global part, so the global part is kept.
  • ite. With Ite-Ok, the condition and then the branch keep the heap (both are analyzed): transitivity. With Ite-Fail, the else branch runs from ss, so the hypothesis for it gives s.g≼s′.gs.g \preceq s'.g directly. The failed condition’s state is discarded, and the proof never needs to know what it did.

The last case shows rollback and the frame property cooperating: the proof would go through even if writesHeap\mathrm{writesHeap} ignored conditions in the Ite-Fail case. What forces the analysis to count them are Ite-Ok, where success commits the condition’s writes, and Ite-Stop, where a return, break or error inside the condition leaves the if without rollback, in the condition’s final state.

7.7 Limits and readings

  • Only writes has a theorem. openverse checks <computes> and <reads> as the front end’s discipline, but the proved property is about the writes bit: a function without it keeps every existing object. A theorem that a <computes> function’s result does not depend on the heap would need a relational (two-run) statement; it is an exercise.
  • The frame and the output are not covered. var local variables live in the frame and are not “the heap”: a <computes> function may use them freely. Printing is not a heap effect either (openverse accepts Verse’s other effect specifiers, such as <converges>, without checking them).
  • Field writes, constructions and rollback. A failed failure context undoes the field writes and the constructions it made, as the opening program shows; this is the heap half of the transactional state of Chapter 3. The reference interpreter implements it by copying the heap on the first write or allocation inside a context. The C runtime rolls back slots and output with the journal of store.c, which has a bounded machine-checked proof (Chapter 8), and object writes and allocations with a field log in its object store (objects.c), which is tested but not proved.

8 Everything Accepted Is Guaranteed

8.1 An opening problem

The theorems of Chapters 4 to 7 had a hypothesis about the program: EffectSound, ProgTyped, WriteSound. The Verse programs in this book were not written in Verse Core. They were written in surface Verse and translated by openverse’s front end, more than five thousand lines of lexer, parser and elaborator that nobody has proved correct. Why should the theorems apply to them?

Here is a program that uses most of what the earlier chapters proved something about: failure, rollback (of a field write, inside logic{…}, which commits on success and undoes on failure), a class with a var field, a generic function and a <reads> function.

chest := class:
    var Gold:int = 0

Peek(C:chest)<reads>:int = C.Gold

Count(Items:[]t, Target:t where t:subtype(comparable)):int =
    var N:int = 0
    for (X : Items, X = Target) { set N += 1 }
    N

Main():void =
    C := chest{}
    for (N : array{5, 12, 7}):
        Added := logic{set C.Gold += N; Peek(C) < 20}
        if (not Added?) { Print("too heavy at {N}") }
    Print("gold: {Peek(C)}")
    Print("rubies: {Count(array{"ruby", "opal", "ruby"}, "ruby")}")

The design that makes this possible is called translation validation. The front end is not trusted to be correct; each program it emits is checked, by Lean functions, and each check is proved to establish the hypotheses of the theorems. The capstone theorem Prog.accepted puts them together.

8.2 The checks

An accepted Verse Core program passes three Boolean checks:

  • check(P)\mathrm{check}(P), the conjunction checkEffectSound(P)∧checkWellScoped(P)∧checkMain(P)∧checkWriteSound(P), \begin{array}{l} \mathrm{checkEffectSound}(P) \wedge \mathrm{checkWellScoped}(P) \\ \quad {}\wedge\ \mathrm{checkMain}(P) \wedge \mathrm{checkWriteSound}(P), \end{array} where checkMain\mathrm{checkMain} says that Main exists and takes no arguments;
  • checkTypes(P,S,Γ→)\mathrm{checkTypes}(P, S, \vec\Gamma), the type checker of Chapter 5, run with signatures SS and a certificate Γ→\vec\Gamma of every function’s slot types;
  • checkControl(P)\mathrm{checkControl}(P), which holds when brkSafe⊥(𝑓𝑛.𝑏𝑜𝑑𝑦)\mathrm{brkSafe}_{\bot}(\mathit{fn}.\mathit{body}) for every function 𝑓𝑛\mathit{fn} of PP.

Each is a computable function, and each has a soundness lemma: Chapter 4’s checkEffectSound gives EffectSound, Chapter 7’s checkWriteSound gives WriteSound, Prog.checkTypes_sound gives ProgTyped. Two we have not met:

Scoping. checkWellScoped\mathrm{checkWellScoped} verifies that every slot index in a function’s body is below its frame size and every call names an existing function with the right number of arguments. Under it, evaluation never raises a slot or call error and never changes the size of a frame:

@Eval.scoped_ok : ∀ {P : Prog},
  P.WellScoped →
    ∀ {s : St} {e : Expr} {r : Res} {s' : St},
      Eval P s e r s' → Expr.scoped P s.fr.length e = true →
        r.scopeErr = false ∧ s'.fr.length = s.fr.length

WellScoped is also exactly what openverse’s C loader validates before it runs a binary, so the C interpreter can use fixed-size frames with no bounds checks of its own. That the C loader really establishes it, for every input buffer up to 4 KiB, is a separate machine-checked proof in Rocq (QuickProof’s law loader_wellscoped).

Control. brkSafeb(e)\mathrm{brkSafe}_{b}(e), with bb recording whether we are inside a loop, is true when every break is inside a loop of the same function body; a for body does not count. Then no break escapes:

@Runs.no_control : ∀ {P : Prog},
  P.checkControl = true → ∀ {r : Res} {out : List Nat},
    Runs P r out → r ≠ Res.err ErrKind.control

8.3 The theorem

Accepted programs (Prog.accepted)

Let PP pass check\mathrm{check}, checkTypes\mathrm{checkTypes} with signatures SS, and checkControl\mathrm{checkControl}, and let Main have type ()→τ() \to \tau. If RunsPro\mathrm{Runs}\ P\ r\ o, then

  1. rr is not a slot or call error;
  2. rr is not a type error;
  3. rr is not a control error;
  4. the final heap is well typed under some Ξ\Xi, and if r=𝗈𝗄vr = \mathsf{ok}\,v then Ξ⊨v:τ\Xi \models v : \tau;
  5. if Main is not <decides>, then r≠𝖿𝖺𝗂𝗅r \neq \mathsf{fail};
  6. every run of PP has outcome rr and output oo.

So the only runtime errors left are 𝖾𝗋𝗋𝑜𝑣𝑒𝑟𝑓𝑙𝑜𝑤\mathsf{err}\,\mathit{overflow} and 𝖾𝗋𝗋𝑢𝑠𝑒𝑟\mathsf{err}\,\mathit{user} (Err()).

@Prog.accepted : ∀ {P : Prog} {S : Sigs} {Γs : List (List VTy)} {τ : VTy},
  P.check = true →
    P.checkTypes S Γs = true →
      P.checkControl = true →
        S.fns[P.main]? = some ([], τ) →
          ∀ {r : Res} {out : List Nat},
            Runs P r out →
              r.scopeErr = false ∧
                r ≠ Res.err ErrKind.type ∧
                  r ≠ Res.err ErrKind.control ∧
                    (∃ fr heap,
                        Eval P Prog.initSt (Expr.call P.main []) r
                            { fr := fr, g := { out := out, heap := heap } } ∧
                          ∃ Ξ, HeapOK S Ξ heap ∧
                            ∀ (v : Value), r = Res.ok v →
                              hasTy Ξ v τ = true) ∧
                      (∀ (fn : Fn), P.fns[P.main]? = some fn →
                          fn.decides = false → r ≠ Res.fail) ∧
                        ∀ (r' : Res) (out' : List Nat), Runs P r' out' →
                          r' = r ∧ out' = out

The statement is a long conjunction, and its proof is short, because each conjunct is a theorem of an earlier chapter applied to the hypothesis its check establishes:

  obtain ⟨hs, hf⟩ := Prog.check_ok hc hr
  obtain ⟨hty, hv⟩ := Runs.typed (Prog.checkTypes_sound ht) hm hr
  exact ⟨hs, hty, Runs.no_control hctl hr, hv, hf,
    fun r' out' h' => Runs.det h' hr⟩

Prog.check_ok packages conjuncts 1 and 5 (scoping and <decides> soundness, from Eval.scoped_ok and Runs.no_fail), Runs.typed gives 2 and 4, Runs.no_control gives 3, and Runs.det gives 6. The heap-effect theorem of Chapter 7 is stated separately as Prog.accepted_no_writes, because it is about individual calls rather than whole runs.

8.4 Why the front end need not be trusted

The front end runs Prog.check, Prog.checkTypes and Prog.checkControl on its own output, and refuses to emit or run a program that fails them. So for every program it accepts, the hypotheses of Prog.accepted hold by computation, whatever bugs the elaborator has. A bug can show up in only two ways:

  • The front end rejects a correct program. An elaborator that emits ill-typed Core is caught by its own checker. This is an inconvenience, not a broken promise. (openverse’s error messages name the function that failed checkTypes precisely so that such bugs can be found.)
  • The front end emits a program that means something else. If the elaborator translated X + 1 as X + 2, the result would still be checked, typed, deterministic and safe: just wrong. Prog.accepted does not say that the Core program is the meaning of the surface program; it says that whatever the meaning is, it is well behaved. Faithfulness of the elaboration is tested, against the Book of Verse and the test suite, not proved.

This is the general bargain of translation validation, and it is a good one: the checkers are small and proved, the translator is large and free to change.

8.5 The remaining errors, and the seam to C

Overflow and Err() remain, by design. Err() is a program asking to stop. Overflow is the reading openverse takes for int: 64-bit, with overflow an error rather than a wrap-around or a failure. Neither is caught by a failure context. The integer division family shows the fine print:

Main():void =
    Low:int = -9223372036854775807 - 1
    if (M := Mod[Low, -1]) { Print("Mod[Low, -1] = {M}") }
    if (Q := Quotient[Low, -1]) { Print("Quotient = {Q}") }

Run in the playground

The remainder of −263-2^{63} by −1-1 is 00, representable; the quotient is 2632^{63}, which is not, so Quotient raises an overflow error. The if does not catch it, the program stops with exit code 2, and only the first line was printed. Lean states this corner exactly:

apply_min_neg_one :
  Prim.floorDiv.apply [Value.int Int64.minV, Value.int (-1)] =
    Res.err ErrKind.overflow ∧
  Prim.ceilDiv.apply [Value.int Int64.minV, Value.int (-1)] =
      Res.err ErrKind.overflow ∧
    Prim.quotient.apply [Value.int Int64.minV, Value.int (-1)] =
        Res.err ErrKind.overflow ∧
      Prim.modulo.apply [Value.int Int64.minV, Value.int (-1)] =
        Res.ok (Value.int 0)

This theorem sits on a seam. openverse’s C runtime implements the integer operations in C, and a separate proof, in Rocq with the QuickProof tool under CompCert’s semantics of C, shows that each C function computes a reference formula written with C99’s truncating / and %. Seams.lean restates each formula in Lean, symbol for symbol, and proves that it is the Lean semantics of the primitive:

@apply_floorDiv : ∀ {a b : Int},
  b ≠ 0 →
    Prim.floorDiv.apply [Value.int a, Value.int b] = Res.ofInt (cFloorDiv a b)

where cFloorDiv a b is “truncate, then subtract one if the remainder is non-zero and its sign differs from the divisor’s”. The two proofs meet at the formula; the one step no tool checks is that the C text and the Lean text are the same formula, and openverse prints them side by side (docs/SEAMS.md) for a human to compare. Here is the semantics they agree on, for negative operands:

Main():void =
    if (A := Floor(-7 / 2), B := Ceil(-7 / 2),

        Print("Floor {A}, Ceil {B}, Quotient {Q}, Mod {M}")
    if (Q := Quotient[7, -2], M := Mod[7, -2]):
        Print("Quotient {Q}, Mod {M}")
    if (not Mod[1, 0]) { Print("Mod by zero fails") }

That is not nothing, but every item is named, and none of them is five thousand lines of elaborator.

8.7 Limits and readings

  • Divergence is outside every theorem (Chapter 1): Runs describes finished runs. openverse reports running out of fuel, recursion depth or memory as a resource limit (exit 3).
  • The C interpreter is not proved. It is a transcription of the Lean interpreter, tested against it on every test program and on random ones. Its slot-and-output rollback store (store.c), its loader and its integer arithmetic are proved, with bounds stated in their laws; its object store and its value heap are not.
  • Meaning is a definition. All of this is relative to the semantics as defined, and that the definition is Verse, as the Book of Verse describes it, is a matter of reading, documented in openverse’s docs/LANGUAGE.md.
